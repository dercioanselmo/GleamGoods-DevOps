# AGENTS.md — GleamGoods-DevOps

Rules for any AI agent implementing or modifying infrastructure in this repo (Terraform, Kubernetes manifests, Helm charts, CI/CD). Written after building `14_Konecta/03_AWS_managed_databases`, where several of these were learned the hard way — see that module's context doc (`context/14_Konecta_03_AWS_managed_databases.context.md`) for the concrete story behind each one.

## 1. "Do it like `<existing module>`" means read that module's actual files, not your memory of the pattern

When asked to mirror an existing module (e.g. "same logic as `08_AWS_managed_databases`"), open and read the **real, current files** of that module before writing anything — not a general idea of "how AWS RDS rotation usually works." This repo's actual patterns have specific, load-bearing details that a generic implementation will miss or get wrong:

- Rotation is **always** the AWS-provided SAR app (`aws_serverlessapplicationrepository_cloudformation_stack`, e.g. `SecretsManagerRDSPostgreSQLRotationMultiUser`) — **never a hand-written Lambda**, even when the SAR app's constraints (one host per secret) seem inconvenient. If a requirement appears to conflict with that constraint, that's a question for the user, not a reason to write custom rotation code. This exact mistake was made and reverted while building `14_Konecta/03_AWS_managed_databases` — a custom Python/pg8000 Lambda was built to rotate one shared secret across 5 RDS hosts, then thrown out entirely once the user pointed out the actual expectation was to mirror `08` (which meant splitting into 5 secrets, not inventing a multi-host rotation mechanism).
- The secret model is always two-tier: a **master secret** (created once, read via a `data` source or, if the project explicitly wants no manual secret creation, a Terraform-managed resource — but either way, **never rotated**, never mounted to app pods) and **per-service app secrets** (container created by Terraform, initial JSON value set **manually out-of-band**, auto-rotated). Don't blur these into one secret that's both the RDS master credential and the thing rotation touches — `08`'s whole design exists to keep those separate.
- The per-service app secret's initial value, and the dedicated least-privilege DB user it represents (e.g. `catalog_app`), are **always** created manually, never by Terraform. There is no Postgres/MySQL role-management provider in use in this repo. Don't introduce one just to remove a manual step — that's a bigger, separate decision.
- Inline security-group ingress blocks, not standalone `aws_security_group_rule` resources, for any SG that already manages ingress via inline blocks (which is all of them here) — mixing the two models causes Terraform to revoke the separately-managed rule on the next unrelated apply. This bit a real production incident once (see `08`'s context doc) and the fix is to always add new rules as additional inline blocks (or a `dynamic "ingress"` block) on the same resource.
- Getting the AWS-side Terraform right is not the whole job. The Kubernetes-side secret delivery (`SecretProviderClass` → Secrets Store CSI Driver → synced `Secret` → `envFrom` → Reloader restart on rotation) is a **separate** piece of work that lives in each application's own Helm chart, documented in full in `SECRETS.md` at the repo root. Don't consider a database/secrets module "done" once `terraform apply` succeeds — check whether the consuming service's chart actually wires up a `SecretProviderClass` yet.

## 2. When a stated requirement conflicts with an established repo pattern, stop and ask — don't silently reconcile it

If following an explicit instruction (e.g. "one shared secret for everything") would require deviating from how this repo already does something functionally load-bearing (e.g. rotation), that's a real conflict, not a design detail to resolve on your own judgment. Say what the conflict is, in concrete terms, and let the user pick a side. Do not:
- Invent a custom mechanism to satisfy both halves of a contradictory requirement.
- Silently narrow the scope of what "mirror X" means until it stops actually conflicting.

Ask, using the two conflicting facts as the options, not an abstract question.

## 3. Applying real infrastructure changes always needs an explicit go-ahead

`terraform plan` (and `terraform validate`, `terraform show`) are safe to run anytime — they're read-only. `terraform apply` and `terraform destroy` are not: confirm before running them, even when the user's request implies they eventually want it applied ("I need it applied before X"). Show the plan's summary line (`N to add, N to change, N to destroy`) and flag anything destructive before proceeding. If a user explicitly says "don't apply anything," that instruction persists for the rest of the working session on that module until they say otherwise — don't re-interpret a later "yes, do this" as authorization to apply unless they actually say so.

AWS CLI (`aws ...`) and `kubectl` are approved for **read-only** use in this repo (`describe-*`, `get-*`, `list-*`) to verify live state before/after Terraform changes — this is genuinely useful for catching drift and confirming an apply actually worked, and was used successfully while building the Konecta module. Never run a mutating AWS CLI or `kubectl` command directly — infrastructure changes go through Terraform (or Helm/ArgoCD for K8s manifests), not ad hoc CLI mutations, so state stays in sync with code.

## 4. `for_each` over near-duplicated resources is fine, and preferred once there are 3+ near-identical instances

`08_AWS_managed_databases` hand-writes separate resource blocks per service (Catalog, Orders) because there are only two. That's a file-organization choice, not the architecture itself. When applying the same pattern to more services (Konecta's 5 databases), using `for_each` over a `locals` map of service names is the right call — it keeps the exact same resource *types* and mechanism, just avoids hand-duplicating 5-10x near-identical blocks. Don't let DRY-ing it up change what gets created; if in doubt, the output of `terraform plan` should create the same shape of resources a hand-written version would, just addressed as `resource_type.name["key"]` instead of `resource_type.name_key`.

**Watch for dependency cycles when a `for_each` map mixes static keys with computed attributes.** If a security group's inline ingress rules reference `for_each`-created Lambda SGs, and those SGs' `for_each` is a map that also carries live resource attributes (e.g. an RDS instance's `.address`) needed elsewhere, Terraform can report a cycle: the DB instance depends on its SG, which depends on the Lambda SGs, which depend on a map that itself depends on the DB instance. Fix: split into two locals — a static set of just the keys (drives any `for_each` that doesn't need live attributes) and a separate map carrying the live attributes (used only by the specific resource that actually needs them, downstream of the DB instances). This is documented concretely in `14_Konecta/03_AWS_managed_databases`'s `c9_01` locals file.

## 5. Repo-wide naming and structure conventions

- Terraform file naming: `c<N>_<name>.tf` or `c<N>_<NN>_<name>.tf`, numbered by concern in the order resources depend on each other (versions/providers → variables → remote state → datasources/locals → shared IAM → per-service resources → rotation, if any). Rotation infrastructure gets its own number block even when it modifies earlier resources' behavior (`08` uses `c10` for rotation despite touching `c6`/`c9`; Konecta's equivalent module uses `c9`).
- `local.name = "${var.business_division}-${var.project_name}"` is the standard naming prefix for most modules (`03`-`05`, `08`, and Konecta's database module) — but not all (`01_remote_backend_s3bucket`, `02_VPC`, `06_Amazon_ECR*` use flat naming with no `business_division`). Check the specific module's existing variables before assuming which convention applies.
- Remote state backend key convention: `<Project>/<concern>/terraform.tfstate` (e.g. `GleamGoods/databases/terraform.tfstate`, `Konecta/ecr/terraform.tfstate`). A module's own README can be stale on this — trust the actual `backend "s3" { key = ... }` block in `c1_versions.tf` over prose docs when they disagree.
- Konecta's Terraform modules consume the **same shared VPC and EKS cluster** as GleamGoods (via `data.terraform_remote_state` pointed at `GleamGoods/vpc` and `GleamGoods/eks`) — Konecta does not get, and should not get, its own VPC/EKS unless explicitly asked.
- Read a target module's own context doc in `context/*.context.md` (if one exists) before reimplementing or extending it — these are written specifically to capture non-obvious decisions and past incidents that aren't visible just from reading the current `.tf` files.

## 6. After finishing infrastructure work, update its context doc

Every numbered module has (or should have) a `context/<NN>_<name>.context.md` — a dense re-implementation brief, not a user-facing README. When you materially change a module's architecture (not just tune a value), update its context doc in the same session: what changed, why, and any wrong turns taken and corrected (like the custom-Lambda detour above) so the next session doesn't repeat them. A stale context doc that describes an abandoned design is worse than no context doc.
